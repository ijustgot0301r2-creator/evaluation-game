# 評価ゲーム — 様相μ計算のゲーム意味論

様相μ計算（modal μ-calculus）の **評価ゲーム / model checking game** を、実際に遊んで体験するためのアプリです。

論理式と様相モデルを入力すると、初期位置からの評価ゲームが構成されます。
**肯定者（Verifier）** に必勝戦略があればその式は真、**否定者（Falsifier）** にあれば偽です。
あなたはどちらの側でも担当でき、残りの側はコンピュータが必勝戦略で打ってきます。

## 使い方

```bash
npm install
npm run dev      # 開発サーバ
npm test         # 自己テスト（下記）
npm run build    # 型検査 + 本番ビルド
```

画面はタブ分けせず、**論理式 → モデル → プレイ** の3つのセクションを縦に並べた
1枚のホワイトボードとしてスクロールして使います。数式はすべて KaTeX で組版しています。

### ① 論理式

構造エディタ方式です。構文木の中の穴（破線の `▢`）を選んでから演算子ボタンを押すと、
その穴が演算子とその子の穴に置き換わります。入力は常に構文木として可視化されます。

扱えるのは **否定標準形**（否定はリテラル `¬p` のボタンとしてのみ提供）で、
かつ **μ と ν が同一の変数を束縛しない** 論理式です。

命題変数と束縛変数（μ/ν で束縛する変数）はどちらも自分で名前を入力する形式で、
入力した文字列はそのまま TeX ソースとして KaTeX に渡されるので、`p_1` や `\alpha` のような
添字・ギリシャ文字も自然に組版されます（空の名前・既に使われている束縛変数名は受け付けません）。
命題変数は 1 個でも 3 個以上でも好きな数だけ追加でき、追加するとその場でモデルの真偽値表にも列が増えます。

構文木の破線の矢印は、束縛変数から対応する `μx` / `νx` への巻き戻しを表します。

### ② モデル

キャンバス上に状態と辺を自由に配置できます。

| モード | 操作 |
| --- | --- |
| 移動 | 状態をドラッグ |
| 状態を追加 | 何もない場所をクリック |
| 辺を追加 | 始点 → 終点の順にクリック（同じ状態を 2 回押すと自己ループ、既存の辺を指定すると削除） |
| 削除 | 状態または辺をクリック |

右側の表で、命題変数の追加・削除、各状態での付値、初期状態の選択ができます
（① の論理式エディタのリテラルボタンは、ここで追加した命題変数と常にリンクしています）。

### ③ プレイ

担当する側を選ぶとゲームが始まります。位置は **(状態, 論理式の木のノード)** の組で、
状態駒がモデル上を、論理式駒が構文木の上を動きます。

| ノード | 動き |
| --- | --- |
| `∧` | 否定者が子を 1 つ選び、論理式駒を 1 つ下へ |
| `∨` | 肯定者が子を 1 つ選び、論理式駒を 1 つ下へ |
| `□` | 否定者が遷移を 1 回選ぶ。論理式駒も 1 つ下へ。遷移できなければ肯定者の勝ちで終了 |
| `◇` | 肯定者が遷移を 1 回選ぶ。論理式駒も 1 つ下へ。遷移できなければ否定者の勝ちで終了 |
| `μx` / `νx` | 一択なので自動で 1 つ下へ |
| 束縛変数 `x` | 自動で `ηx` の 1 つ下へ巻き戻す |
| リテラル / `⊤` / `⊥` | 現在の状態で真なら肯定者、偽なら否定者の勝ちで終了 |

## 無限プレイの扱い

位置が履歴中で **2 度目に現れた時点でループ確定** とし、その区間を無限回繰り返したとみなして終了します。
勝敗は、ループ区間で論理式駒が束縛変数から `ηx` の本体へジャンプした箇所に現れる変数のうち、
**優先度が最も高いもの**（束縛の入れ子で最も外側の変数を最高とする）が
`ν` で束縛されていれば肯定者、`μ` なら否定者の勝ちです。
同じ `ηx` に戻っただけでは判定せず、状態も一致している必要があります。

終了時には、棋譜上でループ区間が網掛け表示され、区間内でジャンプした変数の一覧と、
決め手になった変数およびその束縛子が表示されます。

この「最初の繰り返しで打ち切る」規則は、パリティゲームが記憶なし決定的であることから、
元の無限ゲームと勝者が一致します。コンピュータの戦略も Zielonka の再帰アルゴリズムで求めた
記憶なし戦略なので、両者は整合します。

## 実装のしくみ

評価ゲームはそのままパリティゲームとして符号化されます。

- 位置: `(状態, 構文木のノード)`。`∧` と `□` は否定者、`∨` と `◇` は肯定者の持ちノード。
- 優先度: 束縛変数 `x` のノードに、`2·(外側からの順位の逆順) + (μ なら 1)` を与える。
  外側の束縛ほど大きい値になり、偶数は `ν`（肯定者）、奇数は `μ`（否定者）に対応します。
  その他のノードは優先度 0。構文木の辺は下向きにしか進まないので、閉路は必ず変数の
  巻き戻しを通り、したがって優先度 0 だけの閉路は存在しません。
- 終端（リテラル・`⊤`・`⊥`・遷移先のない `□`/`◇`）からは、勝者に対応する自己ループのシンクへ辺を張ります。
  こうしてアリーナを行き止まりなしにしておくと、Zielonka の再帰がそのまま使えます。

`src/logic/parity.ts` が Zielonka の再帰アルゴリズム（勝ち領域と記憶なし戦略の両方を返す実装）、
`src/logic/game.ts` がゲームの規則とアリーナの構成です。

## 自己テスト

`npm test` は、ゲームの解が **素朴な不動点計算による意味論** と一致するかを検査します。

- 19 種類の論理式 × 2 状態モデルの全列挙（全グラフ 2⁴ × 全付値 2⁴）＋ 3 状態のランダムモデル 400 件
- Zielonka の戦略の健全性（戦略の指す先が後続であり、勝ち領域に留まる）と、勝ち領域の決定性
- **実プレイのシミュレーション**: 勝者側が記憶なし戦略、敗者側がランダムに打つプレイを
  上記のループ規則で打ち切り、その勝敗が常にパリティゲームの解と一致することを確認

約 4.7 万件の検査がすべて通ります。

## デプロイ

`main` への push で GitHub Actions が GitHub Pages へデプロイします
(`.github/workflows/deploy.yml`)。リポジトリの Settings → Pages で
**Source** を **GitHub Actions** にしてください。
`vite.config.ts` の `base: './'` により、`https://<user>.github.io/<repo>/` のような
サブパスでもそのまま動きます。

Pull request と `main` 以外への push では `.github/workflows/ci.yml` が
型検査・自己テスト・ビルドを実行します。
